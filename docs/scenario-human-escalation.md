# 场景迁移评估：判断用户提问是否需要人工介入

> **问题**：抛开现有的合同合规场景，只保留「网关 + SemIf 式判定服务」这一层交互，
> 把业务换成「**判断客户提问是否需要人工介入**」，是否可行？
>
> **结论：可行，而且是最贴合的场景之一。但有一个必须先解决的陷阱（见第 3 节）。**

---

## 1. 为什么这个场景天然适配

回顾这套机制的本质：**输入一份证据 + 一组冻结的候选答案，输出各候选的概率分布。**

「是否需要人工介入」正好是这种形状：

| 要求 | 该场景的对应 |
|---|---|
| 判定是**小而频繁**的 | 每条用户提问一次 |
| 答案是**有限枚举** | 需要人工 / 不需要 / 证据不足 |
| 判据**可自然语言描述** | "这条提问是否需要人工介入？" |
| 输入是**非结构化文本** | 用户提问本身 |
| 结果要**驱动后续动作** | 路由到人工队列 or 自动处理 |

**而且它比合规场景更常见**——任何客服/工单/IM 系统都有这个判定。

---

## 2. 直接迁移的部分 vs 必须重建的部分

### ✅ 原样保留（这才是"网关与 SemIf 的交互"本身）

| 能力 | 说明 |
|---|---|
| **类型化输出 + 概率** | 不生成自然语言，直接读选项槽位 |
| **答案槽位自检** | 启动时断言选项字母是单 token 且往返一致 |
| **prompt 哈希校验** | 证明"实际问了什么"，服务端不符直接 409 |
| **缓存（stateHash）** | 同一提问重复判定零成本 |
| **审计记录** | 每次判定留痕，可回答"为什么升级了/没升级" |
| **降级是一等状态** | 模型挂了返回 DEGRADED + 保守动作，不阻塞主流程 |
| **策略层分离** | 阈值与动作是纯 Java，不在模型里 |
| **评测方法论** | 冻结集、逐行证据、噪声地板、漂移门禁 |

### 🔨 必须重建（业务侧的工作）

| 项 | 为什么必须重建 |
|---|---|
| **判定点定义**（判据 + 选项 + 顺序） | 冻结契约，与业务强相关 |
| **state 里放什么** | 是"只有提问"，还是"提问 + 历史 + 客户等级" |
| **标签（金标）** | 见第 3 节——这是最大的坑 |
| **阈值与动作映射** | 完全由业务代价结构决定 |
| **评测集** | 必须有业务方的真实标注数据 |

---

## 3. ⚠️ 最大的陷阱：标签从哪来

这是整个迁移里**唯一真正困难**的地方。

| 想要的标签 | 现实 |
|---|---|
| "**这条提问本来该不该转人工**" | ❌ **没有这个 ground truth。** 事后无法知道"如果不转人工会怎样" |
| "**这条提问当时有没有转人工**" | ✅ 有记录，但它回答的是另一个问题 |

**"转人工了" ≠ "需要人工"。** 可能是：
- 规则粗暴（关键词命中就转）
- 客服主动兜底
- 客户自己要求转
- 模型答错了被人工补救

**如果直接拿"当时是否转人工"当金标，你训练/评测的是一个「模仿历史规则」的系统，
而不是「判断是否需要人工」的系统。**

### 解法：把判定拆开，只用可观测的证据

**不要问模型"该不该转人工"**（那是动作，且无金标）。**要问它可判定的命题**：

```
❌ 差：「这条提问需要人工介入吗？」
        └─ 模型在做动作决策，且标签不可得

✅ 好：「以下证据是否表明该提问超出了自动处理的能力范围？」
        └─ 模型在判定证据，标签可由「历史人工处理结果」派生
```

**可用的标签来源**（按可信度排序）：

| 来源 | 强度 | 说明 |
|---|---|---|
| 人工处理后的**结论文本**（如"此问题需产品确认"） | 强 | 人工实际给出了模型给不出的答案 |
| **人工介入后修改了自动回复** | 强 | 反证自动回答不充分 |
| 工单被**升级到二线** | 中 | 一线无法解决 |
| 客户**重复提问/明确要求转人工** | 中 | 间接信号 |
| 单纯"转人工了" | **弱** | 见上，有偏 |

## 4. 按这套机制该怎么设计

### 4.1 判定点定义（冻结）

```jsonc
{
  "id": "support.needs_human",
  "version": 1,
  "owner": "support-ops",
  "question": "Does the supplied evidence indicate this request cannot be handled automatically?",
  "options": [
    {"id": "needs_human",  "description": "The request requires human handling."},
    {"id": "automatable",  "description": "The request can be handled automatically."},
    {"id": "insufficient", "description": "The evidence does not settle whether human handling is required."}
  ]
}
```

**三个选项，不是两个。** 显式的"证据不足"出口让模型能弃权——
实测这类弃权出口在证据不足时会显著改变行为，且**正是人工该介入的情况**。

### 4.2 state 里放什么（逐层增加，代价随之上升）

| 层级 | state 内容 | 成本 | 适用 |
|---|---|---|---|
| L1 | 仅用户提问原文 | 极低 | 冒烟验证 |
| L2 | + 会话历史（最近 N 轮） | 中 | 需要区分追问与首问 |
| L3 | + 客户等级 / 历史工单 | 中高 | 需要区分 VIP |
| L4 | + 上游检索到的知识库片段 | 高 | 需要判断"我们有没有答案" |

**从 L1 起步，逐步加。** 每次加字段都必须在冻结评测集上重测——
实测证据：**state 内容的变化对判定结果的影响，远大于模型或硬件的更换。**

### 4.3 分档与动作（业务方策略）

```
needs_human 的 p ≥ 阈值_高  →  直接转人工（宁可多转，不可漏转）
中间带                       →  转人工 + 标记"模型不确定"（供复盘）
automatable 的 p ≥ 阈值_高   →  自动处理
insufficient 占优 或 低置信   →  转人工（保守）
```

**注意代价不对称**：漏转（该转没转）通常远贵于误转（不该转却转了）。
所以阈值应该**偏向转人工**——而这只有业务方能定。

## 5. 上线前必须测的四件事

| # | 测什么 | 怎么测 | 为什么 |
|---|---|---|---|
| 1 | **判定质量** | 在有人工标注的历史样本上测三类判定的准确率 | 没有这个数字，其他都是空谈 |
| 2 | **升级率** | 分档后各档占比 | 直接决定人工工作量增减 |
| 3 | **代价矩阵** | 漏转 vs 误转的业务代价 | 阈值由它反推，不能拍脑袋 |
| 4 | **稳定性** | 同配置重复运行 / 换序 / 加无关上下文 | 实测这三项分别造成 1.4% / 30.6% / 11.1% 的翻转 |

**特别提示第 4 项**：实测**选项呈现顺序**的影响是 **30.6%**，比换一张 GPU（0.7%）大 40 倍。
对这个场景意味着——**"转人工"和"自动处理"哪个排在前面，会显著改变结果**。
选项顺序必须冻结，且改动等同契约变更。

---

## 6. 这个场景比原场景更难的地方

| 难点 | 说明 |
|---|---|
| **标签有偏** | 见第 3 节，历史"是否转人工"不等于"是否需要人工" |
| **代价不对称且难量化** | "漏转一个 VIP"的代价，业务方自己也未必说得清 |
| **分布会漂移** | 用户提问的分布随产品、季节、活动变化，评测集会过期 |
| **反馈闭环慢** | 判定对不对，要等人处理完才知道 |

---

## 7. 结论

**可行，而且改动量比想象的小。**

- **网关与判定服务的交互层完全不用改**——它本来就是业务无关的
- **要重建的是**：判定点定义、state 内容、标签、阈值、评测集
- **最大的工作量不在工程，在标签**：把"是否转人工"翻译成"证据是否表明超出自动处理能力"

**一句话**：
> 这套机制解决的是「**把一份材料，按一组预先冻结的口径，判成一个带概率的枚举**」。
> 换业务只需要换口径和材料；**不需要换模型、不需要重新训练、不需要改网关**。

**但它的天花板也很明确**：
> 它不会让模型更聪明（模型只有 0.813 的准确率），
> 它只是让模型的不可靠**变得可控、可算账、可审计**。
