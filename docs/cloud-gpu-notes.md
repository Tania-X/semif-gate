# 云 GPU 上跑推理服务的实战笔记

> 来源：本项目在一次性租用的 **RTX 4090 PLUS** 云实例上搭建 SemIf 推理链路、
> 完成跨硬件复现与性能基线的全过程。
> 本文只记录**可迁移的技术经验**，不含任何账号、实例或服务商信息。

---

## 1. 选卡：优先「能对照基线」而不是「更快」

本项目要复现 SemIf 的已发布质量数据，而那批数字产自 **RTX 3090**。

**结论：能用基线同款卡就用同款。** 理由不是情怀，是**诊断能力**：

- 结果对得上 → 说明环境配对了
- 结果对不上 → 你能确定是自己配错了，而不是「硬件不同所以没法比」

换一张更快的卡，任何偏差都变成一团浆糊——你无法区分是配置问题还是硬件差异。
实测印证：换到完全不同的 GPU 架构（Ampere → Ada），质量类结论依然复现
（144 行仅 1 行翻转，且该行是精确平局），但**吞吐与延迟完全不可比**。

**所以**：质量验证可以用更快的卡；**吞吐对照必须同款**。

## 2. 环境搭建：三个真实的坑

### 2.1 `pip install -e '.[test]'` 会悄悄换掉锁定版本的 torch

依赖里钉着 `torch==2.10.0`，但直接用国内镜像装依赖时，解析器会拉到**更新的版本**
（实测装成了 2.14.0）。对锁版本的项目来说，这直接破坏可复现性。

**做法**：装完依赖后**显式校验并重装**：

```bash
python -c "import torch; print(torch.__version__, torch.version.cuda)"
# 不符则：
pip uninstall -y torch torchvision torchaudio
pip install "torch==2.10.0" --index-url https://download.pytorch.org/whl/cu128
```

### 2.2 wheel 源的选择比想象的窄

`torch==2.10.0` **在 cu124 源里不存在**（最高只到 2.6.0），必须用 cu128 源。

**教训**：先确认目标版本在哪个索引里有 wheel，再决定镜像。
驱动较旧也能用（CUDA minor version compatibility），不必为了匹配驱动而降级 wheel。

### 2.3 基础镜像经常缺最基础的东西

实测镜像自带 CUDA toolkit，但**没有 pip、没有 curl、没有 pypi 源配置**。

```bash
apt-get install -y python3-pip python3-venv curl
# 并写 /etc/pip.conf 指向可用镜像源
```

**建议**：开机后先跑一遍体检再动手：

```bash
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv,noheader
python3 --version; python3 -m pip --version; nproc; free -g; df -h /
```

## 3. 模型权重下载：换源能差一个数量级

| 源 | 实测速度 | 8.8 GB 耗时 |
|---|---:|---:|
| Hugging Face 镜像 | **0.4 MB/s** | 2 小时以上 |
| **ModelScope** | **5.4–6 MB/s** | **16 分钟** |

**13 倍差距。** 而且 HF 那条路还踩了另一个坑：

```
HF_HUB_DISABLE_XET=1 在 huggingface-hub 1.31.0 上不生效
→ 仍走 Xet 通道 → 401 Unauthorized → 反复 read operation timed out
```

**结论：在国内云主机上，直接用 ModelScope，不要在 HF 上纠缠。**

### 下载后必须校验

不要看到「下载完成」就信。实测校验方式：

```python
import json, os
idx = json.load(open("model.safetensors.index.json"))
declared = idx["metadata"]["total_size"]          # 索引声明的总字节
actual = sum(os.path.getsize(f) for f in set(idx["weight_map"].values()))
assert declared == actual, f"{declared} != {actual}"
```

**再加载一次模型**才是真正的验证——实测加载 8.5 s、显存 7.83 GiB、
参数量 4.21B，与项目文档记录一致，这才算数。

## 4. 大模型服务：延迟与显存

| 项 | 实测（4B bf16） |
|---|---|
| 显存占用 | **9.5 GB** |
| 冷启动（首次推理，含 CUDA 上下文与内核编译） | 数秒 |
| 稳态单次推理（~150 token 输入） | **p50 95 ms** / p95 149 ms |

**两个必须注意的点**：

1. **首次推理特别慢**（内核编译）。任何性能测量都要先做一次**预热**并排除。
2. **同一配置两次运行结果不完全相同**。实测同一份输入、同一配置、
   两次独立运行会翻转 **2/144** 行（最大概率偏移 0.092），
   且翻转全部发生在 margin ≤ 0.124 的行上。

   → **含义**：任何 A/B 对比（换卡、换版本、换参数）都必须先测「噪声地板」，
   否则无法区分真实差异与运行间波动。单次对比得出的结论可能是错的
   （本项目就因此一度错误归因于某个内核库，后经归档数据推翻）。

## 5. 在远程实例上跑长任务的几个实操坑

这些都是实测踩过的，与云服务商无关：

### 5.1 `pkill -f` 会匹配到你自己的 SSH 命令

```bash
ssh host 'pkill -f server.py'     # ❌ 命令行本身含 "server.py"，会话被杀
ssh host 'pkill -f "serve[r].py"' # ✅ 用正则技巧避开自匹配
```

### 5.2 SSH 会等待后台进程

`nohup cmd &` 之后 SSH 仍可能挂住，因为 stdout 未断开。几种可行做法：

- 用 `setsid cmd > log 2>&1 < /dev/null &` 后立即 `exit`
- 或**让 SSH 会话保持存活**（把它本身放进一个后台任务），服务随会话一起活

### 5.3 macOS 没有 `timeout`

`timeout 540 ./cmd` 在 macOS 上直接报 `command not found`，
**而且如果写在管道里，失败会被 `| tail` 吞掉**，看起来像「命令跑了但没输出」。
实测因此白等了一轮。

### 5.4 改完代码记得重启服务并**确认进程是新的**

实测有一次改了服务代码、重启后行为仍是旧的——因为新起的进程失败了，
而旧进程还在监听端口。**改完务必确认进程启动时间晚于文件修改时间**。

## 6. 计费：两个容易误解的地方

### 6.1 「还有 1 小时」不等于「还能免费跑 1 小时」

预留到期时间是**计费终点**。提前结束**会把未用时长按比例退费**，
而不是把时间留到以后。

所以工作做完后继续开着，那笔钱**必然变成机器时间**；
提前释放则**变回余额**。时间对你没价值时，提前释放严格更优。

### 6.2 停止实例 ≠ 释放磁盘

实测这是**两步**，只做第一步的话磁盘仍在按小时计费：

| 步骤 | 效果 |
|---|---|
| 1. 停止/退租 | 实例进入「磁盘保留」状态，**磁盘继续计费** |
| 2. **释放磁盘** | 计费才真正停止 |

**注意**：退租退款可能返回**代金券账户**而非现金（取决于你的扣费优先级设置）。
券通常不能提现，但可继续用于租机器。

### 6.3 保留磁盘 vs 重建环境：算一下再决定

| | 保留磁盘 | 释放后重建 |
|---|---|---|
| 成本 | 磁盘单价 × 容量 × 小时数 | 0 |
| 下次准备 | 0 分钟 | 见下 |

实测数据点：200 GB 盘的保留费约 **0.12 元/小时（2.88 元/天）**；
而重建环境（重下 8.8 GB 权重 + 装依赖）约 **20 分钟**，
按 2.6 元/小时算约 **0.9 元**。

→ **间隔超过约 8 小时，释放就更划算。**

**前提**：代码已进 git，且有幂等的重建脚本。否则「省下的钱」会被人工成本吃掉。

**重建脚本应该做的事**（本项目 `setup-semif-cloud.sh` 的结构，可参考）：

```
0. 环境体检（GPU / 核数 / 内存 / 磁盘）
1. 系统依赖
2. 取代码（已存在则重置到最新）
3. venv + 锁定版本的 torch + 项目依赖
4. 环境验证（打印 torch/cuda/capability，不符就停）
5. 单元测试（不需要权重，快）
6. 下载权重（换 ModelScope）
7. 冒烟推理（跑一次真实调用并断言输出形态）
```

**每一步失败就停**，不要带着坏环境往下走——否则会把环境问题误判成模型问题。

## 7. 释放前的产物归档清单

释放是不可逆的，动手前建议核对：

| 类别 | 是否需要归档 |
|---|---|
| 代码 | ❌ 已进 git 就不需要 |
| 模型权重 | ❌ 可重新下载 |
| venv / 环境 | ❌ 可重建 |
| **推理/评测的逐行输出** | ✅ **必须**——这是花钱跑出来的，重建成本高 |
| **评测报告与日志** | ✅ 必须 |
| **基准输入与映射数据** | ✅ 必须（否则报告不可复现） |
| 服务端临时脚本 | ⚠️ 判断一下：常常是调试残留 |

**实测教训**：本项目在释放前归档时，把此前未取回的预测文件拉回来做完整对比，
**因此推翻了一个早期错误结论**（把「运行间波动」误归因于某个内核库）。
如果直接释放，这个错误会永久留在报告里。

## 8. 一份可直接复用的检查清单

**开机后**

- [ ] `nvidia-smi` 确认卡型、显存、驱动
- [ ] 确认 CUDA 与 torch 版本符合项目锁定值
- [ ] 确认 python / pip / curl 齐备

**下载模型**

- [ ] 优先 ModelScope（或实测更快的源）
- [ ] 校验索引声明字节数 == 实际字节数
- [ ] 真实加载一次模型并确认参数量/显存符合预期

**跑任务**

- [ ] 先预热一次，排除内核编译影响
- [ ] 单进程串行跑，避免 GPU 争用污染计时
- [ ] 需要 A/B 对比时，**先测噪声地板**（同配置重复 N 次）

**收尾**

- [ ] 归档逐行输出、报告、基准输入
- [ ] 代码已推送到 git
- [ ] 停止实例
- [ ] **释放磁盘**（否则仍在计费）
- [ ] 核对余额与退款去向
