# 接入自有业务数据：family 该怎么处理

> 回答：「如果后续引入我们自己的业务数据，我们需要新建 family 吗？还是怎么做？」

---

## 0. 先纠正一个我自己引入的偏差

我在写 Java 基准程序时，**按判据建了 188 个判定点**（`(判据, 选项顺序)` 去重）。
那是为了让基准跑通的 workaround，**不是正确设计**。

**实测数据说明了正确关系**：

| 任务族 | 行数 | 不同判据 | 选项集 |
|---|---:|---:|---|
| evidence_interpretation | 48 | **24** | 一套 |
| rule_application | 48 | **24** | 一套 |
| candidate_selection | 48 | **24** | 一套 |

**一个族里有 24 个不同判据，但只有一套选项。**

而 SemIf 的读法（`core.py::direct_messages`）是：

```python
payload = {
    "evidence":  row["state"],        # 逐行
    "criterion": row["question"],     # 逐行 ← 判据是数据
    "options":   [...],               # 来自冻结定义
}
```

**所以判定点的身份应该是：**

> **判定点 = (选项集, 选项顺序, 模型 revision)**
>
> ~~判据~~ **不属于判定点** —— 它是逐行传入的数据。

**推论**：`semif-service` 的实现是对的（从 `state.criterion` 读）；
需要改的是 Java 基准里「按判据建点」的做法。**这一条记为待修正项。**

## 1. 核心原则

> **family 不是按业务主题分的，是按「判定形状」分的。**
>
> 同一个业务域里的不同判定，只要是**不同的形状**，就是不同的 family。

### 什么叫「同一个形状」

| 形状要素 | 说明 |
|---|---|
| **问的是什么类型的问题** | 事实核查 / 规则适用 / 选择 / 分诊 / 打分 |
| **候选答案是什么样的** | 是三态？是 A/B？是团队列表？ |
| **输出怎么被消费** | 驱动什么动作、误判代价是什么 |

### 反面例子（❌ 常见的错误做法）

| 错误做法 | 为什么错 |
|---|---|
| 按业务主题分组（"客服的判定都算一个族"） | 客服里既有"是否需人工介入"又有"该给哪个团队"，**形状完全不同** |
| 把所有判定塞进一个族 | 选项集不同，字母映射就不同，**契约无法表达** |
| 每个判据建一个族 | 族会膨胀到几百个；而族的意义是**共享形状** |

## 2. 接入流程（四步）

```
① 列出业务里的「判定语句」
   "这单该给哪个团队？" / "这个告警是真的吗？" / "该不该转人工？"

② 把每条判定写成三元组：(问题类型, 候选答案集, 输出用途)

③ 检查是否与已有 family 同形
   是 → 复用，只加判据（数据）
   否 → 新建 family

④ 为每个 family 定：阈值、温度、误判代价
```

### 第 ③ 步怎么判断「同形」

**关键问题：候选答案集能不能复用？**

| 情况 | 处理 |
|---|---|
| 选项集与某个已有族**完全相同** | ✅ 并入该族，只新增判据 |
| 选项集**部分重叠** | ⚠️ 建议新建族。强行合并会让描述变得含糊——而描述含糊会损害判定 |
| 选项集**完全不同** | ✅ 新建族 |

> ⚠️ 特别注意：**选项描述的文字本身影响判定**。
> 为了复用族而把描述改得"通用"一点，很可能同时把判定质量改坏。

## 3. 具体例子：假如你的业务是客服系统

```
┌─────────────────────────────────────────────────────────────────┐
│ 业务域：客服                                                      │
│                                                                  │
│  判定 A: "该不该转人工？"                                          │
│      形状: 三态（需要人工 / 可自动 / 证据不足）                     │
│      误判代价: 漏转 ≫ 误转                                        │
│      → 【新建 family: support.escalation】                        │
│                                                                  │
│  判定 B: "该给哪个团队？"                                          │
│      形状: 多选一（team_a / team_b / team_c / …）                  │
│      误判代价: 中等（转错团队 = 延迟）                             │
│      → 【新建 family: support.routing】                           │
│                                                                  │
│  判定 C: "客户情绪如何？"                                          │
│      形状: 有序分类（愤怒 / 不满 / 中性 / 满意）                    │
│      误判代价: 低（只影响话术）                                     │
│      → 【新建 family: support.sentiment】                         │
│                                                                  │
│  ⚠️ 三个判定同属"客服"，但形状完全不同 → 三个 family              │
│     （它们的选项集、字母映射、阈值、校准参数都不该共享）            │
└─────────────────────────────────────────────────────────────────┘
```

### 什么情况下可以复用已有族

| 场景 | 判断 |
|---|---|
| 你已有「证据是否支持某主张」，现在要判「日志是否表明服务恢复了」 | ✅ **同形**，复用 `evidence_interpretation`，只加判据 |
| 你已有「规则是否允许某动作」，现在要判「这条内部规定是否允许该操作」 | ✅ **同形**，复用 `rule_application` |
| 你要判「哪个候选方案更优」 | ✅ 若候选确实是 A/B 式，可复用 `candidate_selection` |

**复用时不改契约**，只在 state 里传新的 `criterion`。**这正是「判据是数据」的价值。**

## 4. 每个 family 需要单独定的东西

新建 family 不是"加个 JSON 条目"就完了。**每个族都要独立标定**：

| 项 | 为什么必须按族 |
|---|---|
| **阈值** | 误判代价不同 ⇒ 同样的 `p≥0.90` 在三个族里含义不同 |
| **温度（校准）** | ⭐ **已实测**：单一温度会让 `rule_application` 恶化 82%、`candidate_selection` 恶化 5% |
| **评测集** | 每个族要有独立的标注样本 |
| **弃权出口** | 是否需要 `insufficient` 这类选项，取决于该判定能否"不知道" |

**实测证据（我们自己链路上跑出的）**：

| 任务族 | 未校准 ECE | 单一温度校准后 | 变化 |
|---|---:|---:|---|
| evidence_interpretation | 0.0708 | 0.0643 | ✅ 略好 |
| **rule_application** | 0.0643 | **0.1170** | ❌ **恶化 82%** |
| candidate_selection | 0.1254 | 0.1327 | ❌ 略差 |

**所以「共用一套阈值/温度」在实测上是站不住的。**

## 5. 接入时的检查清单

### 设计阶段

- [ ] 把每条业务判定写成（问题类型, 候选答案集, 输出用途）
- [ ] 判断能否复用已有 family；**不要为了复用而修改选项描述**
- [ ] 每个族的**选项描述逐字确定**（表述影响判定）
- [ ] 每个族的**选项顺序确定并冻结**（实测顺序影响 30.6% 的判定）
- [ ] 确定是否需要 **弃权出口**（`insufficient` 之类）
- [ ] 明确每个族的**误判代价**（漏判 vs 误判哪个贵）

### 评测阶段

- [ ] 每族准备**独立标注样本**（百行量级起步）
- [ ] 划出 **train / val / calibration / test 四份独立切分**
- [ ] 跑**可靠性曲线**，按族定阈值
- [ ] 按族拟合**温度**（不要用全局值）
- [ ] ⭐ 先测**噪声地板**（同配置重复跑），否则无法判断"有没有变好"

### 上线阶段

- [ ] 每族的阈值落成**带版本的策略文件**
- [ ] 审计记录里带上 `policyVersion` 与 `pointRef`
- [ ] 留好 `human_outcome` 字段的回收路径（**它会变成训练数据**）

---

## 6. 一句话回答

> **不要按业务主题建 family，要按「判定形状」建。**
>
> **同一个业务域的多个判定，通常应该拆成多个 family**——
> 因为它们的选项集、阈值、校准参数都不一样。
>
> **能复用的是"形状"，不是"业务"。**
> 如果新判定与已有族同形，**只加判据（数据），不改契约**；
> 不同形就新建族，并为它单独做标定。
