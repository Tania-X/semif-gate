# 契约：把 semif-gate 当黑盒用

> 本文描述**不关心内部实现**时的输入输出契约。
> 想理解内部机制（缓存、审计、漂移门禁）请见 [`../ARCHITECTURE.md`](../ARCHITECTURE.md)。

---

## 0. 三层结构：哪些是输入，哪些是黑盒

```
┌─────────────────────────────────────────────────────────────┐
│ 第 1 层：判定点定义（输入，冻结、进版本控制）                  │
│   判据 + 选项集 + 选项顺序 + 模型 revision                    │
│   —— 决定「字母 ↔ 选项」的映射，进而决定 prompt 与模型行为     │
└─────────────────────────────────────────────────────────────┘
                            ↓ 注册
┌─────────────────────────────────────────────────────────────┐
│ 第 2 层：调用（输入，逐次请求）                               │
│   state（证据）+ pointRefs（要问哪些判定点）                  │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：黑盒 ◄── 模型、提示词模板、缓存、审计都在这里面       │
│   一次前向读出声明槽位的 logits → softmax → 分布              │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 第 4 层：输出（契约）                                         │
│   完整概率分布 + 溯源信息（可复现、可审计）                    │
└─────────────────────────────────────────────────────────────┘
```

## 1. 期望输入

### 1.1 判定点定义（注册表，冻结）

```jsonc
{
  "id": "ticket.route",            // 进缓存键；形态受限 [a-z][a-z0-9._-]*
  "version": 3,                    // 进缓存键；改语义必须升版本
  "owner": "platform-team",
  "question": "Which team owns the work described by this evidence?",
  "options": [                     // 2–16 个；【顺序是语义的一部分】
    {"id": "db_team",  "description": "Database, storage, replication, or query performance."},
    {"id": "app_team", "description": "Application logic, API behavior, or deploy artifacts."},
    {"id": "sre",      "description": "Infrastructure, capacity, or availability response."}
  ]
}
```

**三条硬约束**（都由启动自检强制，不满足则拒绝启动）：

| 约束 | 原因 |
|---|---|
| **选项描述必须是冻结常量** | 表述本身影响模型判定。实测同一判据下换措辞会改变结果 |
| **选项顺序必须冻结** | 答案字母按下标分配（`LETTERS[i]`）。实测顺序改变导致 **30.6%** 判定翻转 |
| **`modelRevision` 必须是不可变值** | 禁写 `latest`；它是判定身份的一部分 |

> ⚠️ **常见误解**：以为「同一批选项、换个顺序」是等价的。
> 实测证据：按行内原始顺序渲染 prompt 可 **144/144** 命中已发布哈希，按字典序 **0/144**。
> 而顺序对判定的影响（30.6%）比换一张 GPU（0.7%）大 **40 倍**。

### 1.2 单次调用

```jsonc
// decide(rawState, pointRefs)
{
  "state": {
    "evidence": "Customer cannot access an account after a password reset.",
    "criterion": "…",            // 判据也可逐行传入（见下）
    "…": "…"                     // 其余字段由 StateNormalizer 白名单过滤
  },
  "pointRefs": ["ticket.route@3", "ticket.priority@1"]
}
```

| 字段 | 说明 |
|---|---|
| `state` | **被判断的证据**。字符串 / 对象 / 数组皆可 |
| `pointRefs` | 要执行哪些判定点，格式 `pointId@version` |

**state 是运行时传入的，模型里没有任何业务知识。** 换业务不用换模型，只换 state 与判定点。
（检索该给模型看什么，是上游的事——本项目不做 RAG。）

**关于判据的两种放法**：

| 场景 | 判据放哪 | 效果 |
|---|---|---|
| 判据固定（如「该工单归哪个团队」） | 放**判定点**的 `question` | 一个判定点服务所有行 |
| 判据逐行不同（如「评估这条主张是否成立」） | 放 **state** 里 | 每行的判据不同，但**选项集与顺序仍须固定** |

> 注意：判据若逐行不同，它会进入缓存键 ⇒ 同一份证据问 N 个不同判据 = N 次模型调用。
> 想要「一次 prefill 服务 N 个判据」，需要共享前缀能力（当前**未启用**，见第 5 节）。

## 2. 期望输出

```jsonc
{
  "decisions": {
    "ticket.route": {
      "decisionId": "9f2c…",       // = 缓存键 = 审计主键，确定性可复现
      "pointId": "ticket.route",
      "pointVersion": 3,
      "outcome": "OK",             // OK | DEGRADED
      "distribution": [            // 完整分布，【按 optionId 字典序】
        {"optionId": "app_team", "probability": 0.0991},
        {"optionId": "db_team",  "probability": 0.8582},
        {"optionId": "sre",      "probability": 0.0427}
      ],
      "provenance": {
        "providerId": "http-vllm",
        "modelRevision": "851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a",
        "backend": "cuda:0",
        "promptSha256": "3cc9e3d1…",     // 证明「实际问了什么」
        "registrySha256": "…",
        "optionsSha256": "…",
        "inputTokens": 150,
        "latencyMs": 95
      },
      "degradedReason": null
    }
  },
  "records": [ … ],                  // 审计记录，逐条落盘
  "cacheHits": 0,
  "cacheMisses": 2,
  "providerCalls": 1
}
```

### 输出端的三条保证

| 保证 | 含义 |
|---|---|
| **永远返回完整分布** | 不是「一个被选中的答案」。策略层才能判断「是否处于中间带」，评测层才能算 Brier/ECE |
| **按语义 `optionId` 对齐** | 绝不按位置。调用方拿到后应**按键取值**，不要按下标 |
| **降级是一等状态** | provider 失败时返回 `DEGRADED` + 原因，**不伪装成概率为 0 的判定** |

### 调用方该拿什么做决策

```java
Decision d = result.decision("ticket.route");
if (!d.ok()) {
    // 降级：走保守动作，不要读分布
} else {
    String winner = d.argmaxOption();     // 平局时取 optionId 字典序最小者（确定性）
    double margin  = d.margin();          // top1 - top2
    if (margin < 0.05) {
        // ⚠️ 平局带：不要自动执行
    }
    if (d.probabilityOf("db_team").orElse(0) > 0.9) { … }
}
```

## 3. ⚠️ 三条「期望之外」的明确声明

### 3.1 概率**不是**校准过的置信度

`softmax(选项槽位 logits)` 是**在给定选项下的条件分布**，不是「模型有多确信」。
来源项目自己就标注了 `uncalibrated as decision confidence`。

**推论**：不要直接把 `p > 0.8` 当阈值用。要么先做温度校准
（SemIf 新版有 `benchmarks/calibrate.py`，WANLI 上 ECE 从 0.208 降到 0.069），
要么把阈值调保守并配合人工复核。

### 3.2 输出合法**不代表**判定正确

「类型化输出」保证的是**形态**（一定在声明的选项里、一定是合法分布），
不保证语义正确。实测证据：**

- 36 行缺失证据集上，两个系统**各有一个自信度 >0.8 的错误选择**
- 选项顺序一换，777 个判定翻转 10 个

### 3.3 同一个输入，两次运行可能不同

实测：同机、同配置、两次独立运行会翻转 **2/144** 行
（最大概率偏移 0.092），且全部发生在 `margin ≤ 0.124` 的行上。

**推论**：任何 A/B 对比（换模型、换参数、换硬件）**必须先测噪声地板**，
否则无法区分真实差异与运行间波动。**单次对比得出的结论可能是错的。**

## 4. 失败与降级契约

| 情况 | 行为 |
|---|---|
| provider 超时 / 不可达 | 该判定点 `DEGRADED`，**其他判定点不受影响** |
| 服务端 prompt 哈希不匹配 | 服务端返回 `409`，网关丢弃该结果并 `DEGRADED` |
| 判定点未注册 | 请求失败（`404`）——**不接受运行时凭空定义判定点** |
| 缓存条目溯源校验失败 | 视为未命中，且计入 `staleRejections`（可观测） |
| 所有判定点都降级 | 调用方应走保守动作，不要阻塞主流程 |

**降级时仍然返回真实的 `promptSha256`**（prompt 渲染不依赖模型）——
降级是「没拿到分数」，不是「不知道问了什么」。

## 5. 当前能力边界（黑盒视角）

| 能力 | 状态 |
|---|---|
| 一次调用执行多个判定点 | ✅ 接口支持 |
| **同一 state 的多个判定点共享一次 prefill** | ❌ **未启用** —— 实测给出错误分布，故默认关闭（详见待办） |
| 跨调用的精确缓存 | ✅ 同 state + 同判定点 ⇒ 命中，零模型调用 |
| 语义近邻缓存 | ❌ **刻意不做**（会让缓存键不再是正确性边界） |
| 执行任何业务动作 | ❌ **刻意不做**（网关只返回判定，动作由调用方策略决定） |
| 校准置信度 | ❌ 不提供（见 3.1） |

**吞吐参考（RTX 4090 PLUS，4B bf16，输入约 150 token）**：

```
冷启动  p50 95 ms / p95 149 ms  →  约 9.5 次判定/秒
缓存命中  0.07 ms                →  1583×
```

⚠️ 该数字与 SemIf 已发布的 2.33 / 10.75 / 20.03 decisions/s **不可直接比较**：
硬件不同（3090 vs 4090 PLUS），且它启用了共享前缀复用而本实现未启用；
其基准输入是 8000 字符长文档，本基准是 150 token 短文本。
