# 性能基准：Java 网关 + Python 服务 + Qwen3.5-4B

> 日期：2026-09-25 · 硬件：**RTX 4090 PLUS（改装 48GB）** · 后端：Torch bf16 / CUDA 12.8
> 代码：`semif-gate` @ `PerfBenchMain` · `semif-service` @ 188 点注册表

---

## 1. 先说清楚不能比什么

**SemIf 已发布的吞吐数字（2.33 / 10.75 / 20.03 decisions/s）产自单张 RTX 3090。**
本机是 RTX 4090 PLUS（Ada，sm_89）。跨硬件比吞吐没有意义——那组数字还包含
它的共享前缀复用优化（MLX 与 CUDA 两套实现），本服务出于正确性考虑**默认关闭了前缀复用**。

因此本文所有数字都是**本机自洽基线**，不是对 SemIf 数字的复现或超越。

**可比的部分**：质量类指标（分布、argmax、哈希）——已完成端到端验证，逐位一致（Δ≤2e-7）。

## 2. 测试负载

用 SemIf 的**真实冻结评测集**（authored144 + perturbations108 = 252 行）。

实测其结构：

| 维度 | 数量 |
|---|---:|
| 总行数 | 252 |
| 不同判据 | 108 |
| 不同 evidence | 144 |
| **按 (判据, 选项顺序) 去重后的判定点** | **188** |
| 其中单行判定点 / 多行判定点 | 140 / 48 |

> 这个结构本身是个发现：**同一判据下选项顺序也不同**（36 个判据出现多种顺序）。
> 所以判定点身份必须包含选项顺序——与 `finding-option-order-is-semantic.md` 的结论一致。

## 3. 结果

### 3.1 冷启动（240 次真实推理，零缓存命中）

| 指标 | 值 |
|---|---:|
| 总耗时 | **25.3 s** |
| 吞吐 | **9.48 decisions/s** |
| p50 延迟 | **95 ms** |
| p95 延迟 | **149 ms** |
| provider 调用 | 240（每行一次真实 GPU 推理） |

单次决策 95 ms（p50）包含：Java 网关组装 → HTTP → 服务端渲染与哈希校验 →
一次完整前向（bf16，~150 token）→ 槽位读出 → 回传。

### 3.2 缓存命中

| 指标 | 值 |
|---|---:|
| 单次决策（缓存命中） | **0.07 ms** |
| 相对冷启动加速 | **1583×** |
| 命中时 provider 调用 | **0** |

**这是网关最核心的价值**：完全相同的 state 再次询问时，不触碰模型。

### 3.3 同判定点、新 state（连续 5 遍）

用 96 行子集（48 个判定点、85 个不同 state），连续跑 5 遍：

| 遍次 | 命中 | 未命中 | providerCalls |
|---|---:|---:|---:|
| 第 1 遍 | 90 | 6 | 6 |
| 第 2–5 遍 | 96 | 0 | 0 |

第 1 遍的 90 次命中是因为该子集取自前面已跑过的 240 行，缓存已热——**是时序效应，不是缺陷**。
一旦某 state 出现过，后续同 state 的判定成本降到**微秒级**。

---

## 4. 三个必须一起看的结论

### 4.1 缓存是数量级收益，不是百分比收益

```
冷启动  95 ms  →  命中  0.07 ms   （1583×）
```

任何「同一份文档/工单/告警被反复问到」的场景，收益都在这个量级。
这也解释了为什么缓存键的**正确性**如此关键：一次错误命中不是慢一点，而是直接返回错误答案。

### 4.2 网关自身开销很小

冷启动 p50 95 ms 中，绝大部分是模型前向。网关的组装、哈希、缓存查找、审计写入
与 HTTP 往返合计在**个位数毫秒**量级（命中路径 0.07 ms 就是它的上界估计——
那条路径几乎只做缓存查找与审计）。

### 4.3 缓存键必须包含判断点身份，否则会错

本基准构建判定点时曾试图按任务族划分（3 个点），结果**同一判据下出现的不同选项顺序
会命中同一个缓存条目**——而实测选项顺序对判定的影响达 **30.6%**。
最终按 (判据, 选项顺序) 划分成 188 个判定点，缓存语义才正确。

## 5. 未测的部分

| 项 | 状态 |
|---|---|
| 并发/多 worker | ❌ 未测（服务是单进程同步的） |
| 长 state（推理成本随 token 线性增长） | ❌ 未测（本评测集 evidence 约 150 token） |
| 共享前缀复用（`--prefix-reuse`） | ❌ 未测——**实测它在本模型上给出错误分布**，已默认禁用 |
| `causal_conv1d` / `fla` 内核优化 | ❌ 未装（实测 `fla` 更慢；其对判定的影响无法与运行间波动区分） |
| 与 SemIf 已发布吞吐对照 | ❌ 不可比（硬件不同；且它启用了前缀复用） |
| **运行间波动（噪声地板）** | ❌ **未测，但已确认存在**——见下 |

### 5.1 一个必须写进协议的前提：运行间波动

归档分析发现：**同机、同配置、两次独立 `direct` 运行会翻转 2/144 行**
（最大概率偏移 0.0919，全部发生在 margin ≤ 0.124 的行上）。

这对本基准的含义：

- 单次测量的 p50/p95 **在 1.4% 量级的翻转上是不可复现的**；
  上表的吞吐与延迟是**量级证据**，不是逐位可复现的结论。
- 本基准**已在开头固定做一次预热**——若波动源于 CUDA autotuning，
  「是否预热」本身就是变量，必须固定。
- 任何后续的性能或漂移对比，都应先跑同配置 N 次确定噪声地板，再判断候选是否越界。

详见 `reproduction-4090plus-2026-09-25.md` 第 13 节。

## 6. 复现方式

```bash
# 1. 启动判定服务（需 SemIf 与其模型权重）
python server.py --model <模型目录> --revision 851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a

# 2. 跑基准（fixture / registry / mapping 三份文件同源生成）
java -cp <classpath> com.semif.gate.e2e.PerfBenchMain \
    http://127.0.0.1:8080 \
    perf-input-252.jsonl \
    decision-points.json \
    perf-mapping.json \
    240 \
    perf-same-point-new-state.jsonl
```

基准会先做一次预热（排除首次 CUDA 上下文与内核编译），再依次跑
全冷 / 全热 / 混合 / 同判定点新 state 四轮。
